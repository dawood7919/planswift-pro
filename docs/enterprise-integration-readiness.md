# جاهزية التكامل المؤسسي

## الحالة والقرار

تستخدم المنصة الآن Manus OAuth لحسابات الأفراد، ولا يوجد موفر هوية مؤسسي معتمد أو بيانات اعتماد مسلّمة لهذه البيئة. لذلك **لم يُنشأ تكامل SSO أو SCIM صوري** ولم تُخزَّن أسرار أو عناوين افتراضية في المصدر. يضمن هذا القرار ألا يبدو الوصول المؤسسي متاحاً بينما لا توجد جهة هوية موثوقة ولا مسار إبطال قابل للتدقيق.

> لا يكفي إنشاء حقل `organizationId` منفرداً لتحقيق فصل المستأجرين؛ يجب أن يكون نطاق المستأجر جزءاً من كل استعلام محمي وحارس تخويل واختبار ملكية قبل عرض أي مشروع أو ملف أو مراجعة.

OpenID Connect طبقة هوية فوق OAuth 2.0 وتعرّف تبادل Claims للتحقق من هوية المستخدم؛ لذا يعتمد مسار OIDC في Takeoff على تدفق Authorization Code، والتحقق من `iss` و`aud` و`exp` و`nonce` قبل إنشاء جلسة تطبيق. [1] أما SAML 2.0 فهو إطار XML لتبادل معلومات الهوية بين أطراف الأعمال، ويتطلب تبادل metadata ومفاتيح التحقق ونقاط النهاية المتفق عليها. [2] ولإدارة دورة حياة المستخدمين والمجموعات، يعرّف SCIM بروتوكول HTTP معياري للتزويد والإدارة في بيئات المؤسسة والسحابة. [3]

| طبقة التنفيذ | العقد الذي سيُعتمد | شرط القبول قبل التفعيل |
|---|---|---|
| موفر الهوية | OIDC Authorization Code + PKCE **أو** SAML 2.0 Web SSO؛ issuer/entity ID وredirect URIs مقيّدة بالدومينات المنتجة. | تحقق توقيع/claims وسيناريوهات success، رفض issuer وaudience وnonce غير المطابقة. |
| المستأجر | `organizations` و`organization_memberships` و`project.organizationId`، مع دور `owner` أو `admin` أو `estimator` أو `viewer`. | كل قراءة وكتابة للبيانات والمستندات والمراجعات تمر بمحدد عضوية المؤسسة والمشروع. |
| التزويد | `/scim/v2/Users` و`/scim/v2/Groups` بحساب خدمة مخصص قابل للإبطال، وعمليات PATCH وdeactivate تدقيقية. | إنشاء وتحديث وتعطيل مستخدم لا يترك أي جلسة أو عضوية أو وصول للمشروع بعد الإبطال. |
| السجل | حدث غير قابل للتعديل لعمليات تسجيل الدخول والعضوية وتبديل الدور والتزويد والتصدير. | إمكانية استخراج سجل المؤسسة بزمن UTC ومعرّف الفاعل والنتيجة والسياق. |

## متطلبات موفر الهوية عند اعتماده

عند اختيار موفر الهوية، يجب توفير **بيئة اختبار منفصلة** أولاً، ثم قيمة issuer أو metadata URL، وclient ID، وطريقة اعتماد العميل، وشهادات توقيع SAML أو JWKS، وredirect/logout URLs المعتمدة، ومجموعة Claims للمعرّف الثابت والبريد والاسم والمجموعات، وطريقة إنشاء رمز SCIM وتدويره. تحفظ القيم السرية في إعدادات البيئة فقط ولا تدخل git أو حزمة Android.

| قرار يجب اعتماده | افتراض آمن مقترح | أثر القرار |
|---|---|---|
| البروتوكول الأساسي | OIDC مع Authorization Code وPKCE للتطبيقات الحديثة؛ SAML عند اشتراط المؤسسة له. | يحدد مكتبة العميل ومسار callback وبيانات metadata. |
| مفتاح المستخدم | زوج `(issuer, subject)` بدلاً من البريد الإلكتروني. | يمنع إعادة ربط حساب مختلف تغيّر بريده أو نُقل بين مستأجرين. |
| ربط المجموعة بالدور | خريطة صريحة من group IDs إلى أدوار Takeoff، لا أسماء عرض قابلة للتغيير. | يمنع رفع الصلاحية عند تغيير اسم المجموعة. |
| إبطال الوصول | تعطيل SCIM أو إزالة المجموعة يفك العضوية ويجبر تسجيل الخروج من المؤسسة. | يلزم اختبار تأثير الإبطال على web وAndroid. |

## خطة التفعيل بعد الاعتماد

1. يضاف نموذج المؤسسة والعضوية أولاً وتُرحّل المشاريع الحالية إلى مؤسسة شخصية لكل مالك من دون تغيير الملكية الفردية.
2. يضاف تحقق OIDC أو SAML في بيئة اختبار بمزود حقيقي، مع منع أي callback أو issuer أو audience غير مسجّل.
3. تُستبدل فحوص `ownerId` المنفردة بحارس عضوية ونطاق مؤسسة في كل مسار مشروع وPDF ومراجعة وتصدير وواجهة Android.
4. يضاف خادم SCIM المحمي على TLS، مع حساب خدمة محدود وسجل تدقيق واختبارات إنشاء وتعديل وتعطيل واستعلام متعدد الصفحات.
5. تُجرى اختبارات فصل المستأجرين من حسابين ومؤسستين وعضو مسحوب، ثم مراجعة أمنية قبل فتح الإعداد في الإنتاج.

لا يمكن إكمال الخطوتين الثانية والرابعة بشكل حقيقي قبل وجود موفر هوية ومعلومات تسجيله؛ القيام بذلك دونها سيؤدي إلى إعدادات وهمية أو أسرار افتراضية غير آمنة. تظل هذه الوثيقة عقد التنفيذ المعتمد حتى تزويد بيئة الاختبار.
